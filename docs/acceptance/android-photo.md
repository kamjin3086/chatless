# Android photo acceptance (#215)

Run on an ARM64 Android phone. Record app/build commit, Android version, device and camera/picker app, provider/model and request strategy, and which checks passed. An APK build and fake-native/provider tests do not cover the system surfaces.

- With a text draft in chat, open the attachment menu and **Take a photo**. Check that Android's camera opens without a new app camera/storage permission. Capture and accept a portrait; check the preview orientation and the existing text. Repeat with **Choose a photo** for a landscape image and a detailed label/sign. Verify the preview shows enough detail to ask a question about it; record where the compatibility resizing loses text.
- Before Send, watch the configured test provider or a request counter. Neither acquisition, preview, removal, model change nor cancellation may send the photo. Use system Back during capture and while picking; return to the previous conversation, draft text and previous preview. Remove the current photo using the visible remove button; check it is gone without clearing the text.
- With a photo and question drafted, choose a text-only model or a model on an unsupported route, such as strict OpenAI, OpenAI Responses or Anthropic. Confirm that the composer shows the selected model and provider, states that photo sending is unsupported, and sends neither image nor text. Switch to a known vision-capable model on a supported route, confirm the recipient updates, and tap Send. Verify an answer about the actual photo, one image-bearing user turn, and cleared draft only after the provider responds. Reopen the conversation and check the sent photo remains visible.
- Start with no open conversation, stage a photo and question, and reproduce a pre-response rejection (for example, HTTP 400 or an insufficient context budget). Confirm the same photo and text remain in the newly created conversation, with a retry/smaller-image/larger-context hint. Retry from the composer after restoring the endpoint or budget. Repeat from an existing conversation and try Stop before a response. If a reply is active, the composer must not queue the photo as steering. If the model responds while the user is editing the draft, the acknowledgement must not clear their newer text. Switch conversations while a first send is pending; the photo must not appear in an unrelated chat.
- Exercise Phone Photo Picker when available and the AndroidX fallback on an older phone if available. Try an unsupported/corrupt image or one above the 32 MiB source limit; a failure must not replace the current draft/preview. Check touch targets and contrast in light/dark mode and with larger text.

## Compatibility and reuse

- Android uses the system camera with a one-file grant into a dedicated app-private cache path. The picker accepts an image-scoped content URI only; the URI is not a filesystem path or a WebView capability. Temporary material is deleted after import/cancellation and swept at the next acquisition after process death. An unsent preview is held in the composer, not uploaded or persisted as a chat attachment.
- Preview and Send share the same orientation-corrected, metadata-free JPEG (up to 2,048 pixels on the long edge and 120 KiB). The latter is an interim compatibility limit: the existing chat budget counts base64 as text, so even this size can exceed a small configured context window. Shared image-token accounting and image support for OpenAI Responses/Anthropic are separate follow-ups.
- Photo sends support vision models on verified OpenAI-compatible Chat Completions, Gemini, or Ollama routes. A multi-strategy adapter without an explicit supported strategy is not offered for photo sends. The shared send compares the displayed provider, model and route again before dispatch; an unsupported or changed route must not receive a text-only substitute. Strict OpenAI is distinct from OpenAI-compatible Chat Completions: the strict parser rejects payloads without `data:`, but both `SSEClient`'s browser path and the Rust SSE bridge strip that prefix. The follow-up regression should send `data: {"choices":[{"delta":{"content":"A book"}}]}` then `data: [DONE]` through each transport and assert that the strict adapter emits `content_token` and calls completion once. Do not switch strategies behind the model selection.
- #218 can reuse the system picker contract in `AndroidPhotoPlugin.kt` (use AndroidX `PickMultipleVisualMedia` with a selection cap for the batch) and the local bounded content-URI read seam `copySelectedAndroidPhoto` in `AndroidPhotoImport.kt`. Reuse the picker and scoped reading, not `acquire_android_photo`'s single JPEG preview receipt: local photo organization needs task-scoped handles and any necessary metadata before normalization, not conversation image payloads or transferable URIs.
