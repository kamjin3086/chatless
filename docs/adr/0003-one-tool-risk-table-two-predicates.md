# One tool-risk table, two predicates, membership deliberately not widened

Three places in the pipeline answered "is this tool read-only" with their own per-server name regex - the approval decision, the plan-mode gate and the retry decision, all in `src/lib/mcp/pipeline/ToolExecutionPipeline.ts` - while a fourth derived the filesystem permission kind from the same tool names with an if-cascade. They are not the same question: "may this run while planning" and "would replaying this add a side effect" happened to share a regex. We replaced all four with one explicit `server + tool → risk` table plus two derived predicates.

Membership was not widened while consolidating — the table is the union of what the old lists actually contained, nothing more. That matters because `filesystemOp` keeps its existing fail-open default of `read` for unrecognised tool names: names like `list_files` and `search_files` are *not* registered under `fs`, so neither predicate lets an fs call through under those names. That looks like an oversight and is not one; registering them would silently make them plan-allowed and replayable.

Consequence: adding an fs tool name to the table is a security-relevant edit, not a cleanup. Whether a name is registered at all is what decides if plan mode lets it through - `fs`'s `read` is registered, `fs`'s `list_files` is not, and nothing about the two names hints at that difference.

Amendment (one row still answers the gate twice). For `system` the approval predicate keeps its own name list instead of asking the table, and the two lists differ: the gate lets the `system` server's `list_skills` through while the table never registered it (it knows `list_prompts` and `get_prompt`). `list_skills` is also no longer routable - `SystemToolAdapter` routes the six prompt tools - so the extra name is a harmless leftover of the old cascade, but it is exactly the kind of second list this decision was meant to end. Until that row reads from the table - tracked as #256 - "one fact" holds for `fs` and the built-in `skill` row, not for `system`.

Two notes on what "read" means here. `skill__check_deps` is registered as a read, so it is plan-allowed and approval-free, but it is a *probe*: it spawns `npx` / `npm` / `pnpm` / `bun` / `yarn` to ask for versions. Bounded and write-free, so the classification holds - it is just not "reads a file". And `search_files` is still routed by the filesystem adapter while the table leaves it unregistered, so plan mode blocks a call that would in fact only read; registering it is the fix, and this ADR's warning that registration is a security-relevant edit is why nobody has done it casually.

Status: accepted, and on `main` - the table (`src/lib/mcp/pipeline/policy/toolRisk.ts`), `filesystemOp` and their oracle tests shipped.

Amendment (skill aliases). `skill`'s row originally carried the alias names `use`, `read_file` and `list_files` because the adapter routed them. Those aliases had no caller and were deleted with the adapter branches, and the row narrowed with them: a name nothing routes must not stay plan-allowed. The oracle test now skips exactly these three names and a separate test owns the narrowing, so "the table equals the cascades it replaced" still holds for every name that can arrive.

Amendment (two real reads registered). `list_resources` and `get_template` were never in the row - only their old alias names were - while the skill index now actively tells the model to call them to read a file a guide points at. They read files inside the skill package and nothing else, so they are registered as reads: plan mode lets them through, and `skill` is still outside `REPLAYABLE_SERVERS`, so retry behaviour is unchanged. This is the widening the original decision warned about - a deliberate, named one, not a cleanup.

Amendment (retired names are display history). A conversation recorded while `skill__use` and its siblings were routable replays a name the tool set no longer has, and the call's result is already in the message. The card says the tool was removed, and nothing routes the name: the adapter answers every retired name with `Unknown skill tool` and `toolRisk` scores it `unknown`, which `src/lib/mcp/pipeline/__tests__/retiredSkillToolRouting.test.ts` pins for all eight names in both directions. Display tolerance therefore does not re-open the door this ADR closed. The card prints today's equivalent name (`skill__use -> skill__guide`) as text only - no code reads that table to reach a tool, so the choice stays the display door and not a second name map.

Amendment (one gate's answer for the built-in skill row). The approval predicate `decideServerCall` carried its own skill name list, and it had drifted the way a second list always drifts: it still treated the retired `use` / `read_file` / `list_files` as reads, and it did not know `skill__list_resources` or `skill__get_template` - the two live reads the previous amendment registered - so every call the index sends the model to make cost an approval click. The row now reads the answer from `toolRisk`: a registered read is plan-allowed and approval-free from one fact, anything else asks. The external `skills` server keeps its own approval list, because its tool names are that package's business and not this table's. Two names were removed from the equality oracle to do this (`skill`, `SKILL`), and the row is owned by a test that enumerates it instead.
