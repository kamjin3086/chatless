# Tool policy is pure; the pipeline owns every side effect

Approving a tool call means waiting for a human, and the trust they hand over has to be persisted — so the natural shape was a policy module that does the asking and the granting itself. We decided against it: `decideFilesystemCall`, `decideServerCall`, `planFilesystemPromotion` and `planShellPromotion` are pure functions that take the already-resolved inputs as plain arguments and return a decision or a state delta, while the pipeline reads those inputs once, waits for the user, and performs every store write, Tauri call and grant registration.

The alternative would have made the rules untestable without a live store, a database and a waiting user — which is exactly what the existing interface tests pay today with eight mocks. As written, the decisions and promotions themselves are covered by mock-free table tests (policy/__tests__/policy.test.ts, toolRisk.test.ts). The approval round-trip still needs the store and database mocks - depth moved the cost, it did not remove it.
