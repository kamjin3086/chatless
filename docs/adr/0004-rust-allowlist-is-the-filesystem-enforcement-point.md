# Filesystem enforcement lives in the Rust allowlist; plugin-fs stays inside app-owned roots

Two directory lists enforced the same thing in two languages. `assertPermission` checked a `user_fs` list in TypeScript and then read through Tauri `plugin-fs`; the pipeline's filesystem gate checked the allowlist, which is mirrored into the Rust commands where real file access happens. Settings managed only the second list, and `filesystemAllowlistStore` already stated it deliberately does not migrate the first. We treated the Rust allowlist behind the `filesystem_*` commands as the single enforcement point, and deleted the `user_fs` side rather than migrating it: the list had no writer left, the UI could not inspect or revoke it, and the main window's `fs:scope` is `$APPDATA`/`$APPLOG`, so nothing travelling that path could reach a user directory anyway.

Two nails hold the boundary so the next person does not have to rediscover it: `fs:scope` must stay inside those two roots, and no adapter may claim a retired server name. Retired servers therefore fail at routing with `NO_ADAPTER`, which happens before the approval gate - a replayed or hallucinated `user_fs` call cannot open a card the user has no way to honour. `toolNaming` still parses the old names, because they appear in historical conversations.

This does not make plugin-fs safe for user files, and does not claim it was: skills and settings keep using plugin-fs inside the app-owned roots, which is what the scope is for. It also does not add enforcement to the `fs` server, which was already Rust-backed - the point of this decision is that there is now exactly one place to look when asking whether a path may be touched.
