# The phone has no POSIX tool surface: Android is its own runtime, not Linux

The Android client asked the model to behave like a desktop. `getRuntimePlatform` only knew `windows`/`macos`/`linux`, and an Android WebView says `Linux; Android 14` in its user agent, so the phone was reported as Linux and given the shell rules and `ls`/`cat`/`mkdir` examples that go with it. The `core` tool group added to that: the full desktop `fs` and `shell` tool sets were advertised on the phone, where `mobile.rs` registers neither the `filesystem_*` commands nor the process ones. So the model wrote `~/Downloads`, `fs__ls` failed while establishing the call-scoped grant (`CALL_SCOPE_FAILED`), `shell__run` failed with `SHELL_UNAVAILABLE`, and each failure read like a wrong path, which bought another retry on another guess.

Android is now a first-class runtime platform. `getRuntimePlatform` returns `android` (from the OS plugin, and from the user agent before the bare `linux` match), and the `runtime-environment` block for it has no `Shell:` line and no command examples - it states there is no shell, no home directory, and that files come only from what the chat holds. Which tools the phone offers is decided by one predicate, `isMobileUnsupportedServer`, that both `getToolsForGroup` (catalog, and therefore `tools__search` too) and the pipeline guard read: the core group loses `fs` and `shell`, and a call that arrives anyway - from an old conversation, or a model working on prompt-level tool calls - fails with `ANDROID_TOOL_UNAVAILABLE` and the alternative it should have used, before the approval gate and before any grant. One list, two readers, same as ADR 0003.

This does not give the phone a file layer. Files on Android come from what the user handed over: an attached folder (`android_directory__inventory`), selected photos, an attached document. A MediaStore-backed listing of Download/DCIM would be new capability with its own permission semantics, not part of this decision. The guard is a compile-time fact about the mobile composition root: if `mobile.rs` ever registers the `filesystem_*` commands, deleting `mobileUnsupported.ts` is the whole change.
