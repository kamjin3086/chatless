tools__* — tool discovery and loading

## Design principle

"Fewer tools, smarter model"

Tools are loaded on demand so a long tool list does not dilute attention.

## tools__search

Searches the complete tool catalog by tool name or description. A capability
group that matches becomes available in the **next** model step.

```
tools__search({ query: "run a command" })
tools__search({ query: "knowledge base", limit: 20 })
```

Parameters:

| Parameter | Meaning |
|-----------|---------|
| query | tool or capability keywords (required) |
| cursor | zero-based result offset, for paging |
| limit | maximum results (default 20, max 50) |

**When to use it**:
- the loaded tools cannot finish the task
- you want to know what else the system can offer

The core tools (files, shell, web, tool_result) are always loaded and are not
part of the catalog.

## Capability groups

Beyond the core tools the system has these groups. They are not in the request
until something asks for them:

| Group | Contains | Use for |
|-------|----------|---------|
| skill | skill__* | querying skills, managing skill resources |
| prompt | system__* | listing, creating, editing and deleting prompts |
| knowledge | knowledge__list, knowledge__search, knowledge__read | searching and reading the knowledge base mounted in this session |

knowledge is different: it is decided per turn from what the session has
mounted, so it appears and disappears on its own.

## Workflow

### Example: a command has to run

1. notice that shell__run is not in the tool list
2. `tools__search({ query: "run a command" })`
3. carry on describing the task; the tool is available next step

### Example: a file has to be downloaded

1. notice that web__download is missing
2. `tools__search({ query: "download a file" })`
3. continue the task

## Notes

- a search result is a catalog entry, not permission: the group still has to be
  in the next request before you can call it
- do not search repeatedly for the same capability
